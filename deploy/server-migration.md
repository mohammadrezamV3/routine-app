# مهاجرت به سرور جدید (بدون از دست دادن داده و بدون قطعی طولانی)

قاعده‌ی طلایی: **سرور قدیمی را تا وقتی سرور جدید کامل تست نشده پاک نکن.**
ترتیب درست این است: سرور جدید را کامل بالا بیاور → تست کن → DNS را عوض کن →
چند روز صبر کن → تازه آن‌وقت سرور قدیمی را حذف کن.

## حالت ساده: سرور فعلی هنوز داده‌ی واقعی ندارد

اگر روی سرور قدیمی هنوز داده‌ی کاربران نیست، کل بخش بکاپ/ریستور و رقص DNS
لازم نیست. فقط این‌ها:

1. **از سرور قدیمی فقط `.env` را بردار.** کلیدهایی که *نمی‌توانی* خودت
   دوباره بسازی و باید عیناً منتقل شوند چون به پنل سرویس بیرونی وصل‌اند:
   `GOOGLE_CLIENT_ID` / `GOOGLE_CLIENT_SECRET`، `MELIPAYAMAK_*`،
   `ARVAN_AI_*`، `ZIBAL_MERCHANT_KEY`، `SMTP_*`.
   بقیه (`NEXTAUTH_SECRET`، `CRON_SECRET`، کلیدهای VAPID) چون هنوز نه
   نشستی هست نه اشتراک نوتیفی، می‌توانی روی سرور جدید از نو بسازی:
   `openssl rand -hex 32` و برای VAPID `npx web-push generate-vapid-keys`.
2. روی سرور جدید:
   ```bash
   curl -fsSL https://get.docker.com | sh
   ufw allow 22 && ufw allow 80 && ufw allow 443 && ufw enable
   git clone <repo-url> /opt/routine-app && cd /opt/routine-app
   # .env را بگذار (بخش ۲ پایین را برای مقادیر ببین)
   bash deploy/update.sh
   ```
3. **دیتابیس خالی را seed کن** (پلن‌ها/ماژول‌ها و کاربر سوپرادمین):
   ```bash
   # SUPERADMIN_USERNAME و SUPERADMIN_PASSWORD را اول در .env بگذار
   docker compose --profile tools run --rm --build migrate npm run seed
   ```
   بدون seed، جدول `Plan`/`PlanModule` خالی می‌ماند و ثبت‌نام دوره‌ی
   آزمایشی نمی‌گیرد.
4. nginx + TLS (بخش ۴)، crontab (بخش ۵)، تست‌های بخش ۶، و بعد رکورد A را
   به IP جدید بده. چون داده‌ای نیست، سرور قدیمی را هر وقت خواستی پاک کن.

---

## ۰) قبل از هرچیز: چه چیزهایی «حالت» (state) این سایت‌اند؟

- **دیتابیس Postgres** — همه‌چیز این‌جاست: کاربرها، برنامه‌ها، تریدها،
  اشتراک‌ها، **و حتی عکس پروفایل/بنر** (چون به‌شکل data URL داخل ردیف کاربر
  ذخیره می‌شوند، نه فایل روی دیسک). یعنی dump دیتابیس = کل داده‌ی سایت.
- **فایل `.env` سرور** — کلیدها و رمزها. هیچ‌جای دیگری نسخه ندارد.
- **crontab سرور** — خط‌های `deploy/cron.example`.
- **کانفیگ nginx و گواهی TLS** — از `deploy/nginx.conf.example` قابل بازسازی.

پوشه‌ی آپلود جداگانه‌ای وجود ندارد، پس چیز دیگری روی دیسک نیست که نیاز به
کپی داشته باشد.

## ۱) روی سرور قدیمی: بکاپ کامل

```bash
cd /path/to/routine-app

# ۱.۱ بکاپ دیتابیس (از داخل کانتینر db)
docker compose exec -T db pg_dump -U routine -Fc routine > ~/arion-$(date +%F-%H%M).dump

# ۱.۲ بکاپ .env و crontab
cp .env ~/arion-env-$(date +%F).backup
crontab -l > ~/arion-crontab-$(date +%F).txt

# ۱.۳ سلامت بکاپ را همین‌جا چک کن (باید لیست جدول‌ها را نشان دهد)
pg_restore -l ~/arion-*.dump | head
```

هر سه فایل را روی کامپیوتر خودت هم دانلود کن (`scp`)، نه فقط روی خود سرور.

> ⚠️ `docker compose down -v` روی سرور قدیمی، **volume دیتابیس را پاک
> می‌کند**. تا وقتی بکاپ را تست نکرده‌ای این دستور را نزن.

## ۲) روی سرور جدید: آماده‌سازی

```bash
# داکر
curl -fsSL https://get.docker.com | sh
# فایروال: فقط ۲۲/۸۰/۴۴۳
ufw allow 22 && ufw allow 80 && ufw allow 443 && ufw enable

git clone <repo-url> /opt/routine-app
cd /opt/routine-app
```

`.env` را از بکاپ بگذار. این مقدارها **باید عیناً همان قبلی بمانند**:

| متغیر | اگر عوض شود چه می‌شود |
|---|---|
| `NEXTAUTH_SECRET` | همه‌ی کاربرها یک‌باره از حساب بیرون می‌افتند |
| `VAPID_PRIVATE_KEY` / `NEXT_PUBLIC_VAPID_PUBLIC_KEY` | همه‌ی اشتراک‌های نوتیفیکیشن باطل می‌شوند و push دیگر نمی‌رسد |
| `POSTGRES_PASSWORD` | باید با dump هماهنگ باشد (یا هم در `.env` هم موقع restore یکی باشد) |
| `CRON_SECRET` | خط‌های crontab هم باید همین را بفرستند |

این‌ها را هم چک کن که با دامنه/شرایط جدید بخوانند: `NEXTAUTH_URL`،
`NEXT_PUBLIC_SITE_URL`، `AUTH_COOKIE_SECURE`، `TRUST_PROXY_HEADERS`
(اگر nginx/Cloudflare جلوی اپ است باید `1` باشد، وگرنه rate limiting همه را
یک IP می‌بیند)، و `WEB_CONCURRENCY`/`NODE_HEAP_MB` متناسب با رم سرور جدید
(قاعده‌ی سرانگشتی: `WEB_CONCURRENCY × NODE_HEAP_MB` کمتر از نصف رم).

## ۳) بالا آوردن و برگرداندن دیتابیس

```bash
# فقط دیتابیس را بالا بیاور
docker compose up -d db

# اسکیمای خالی را بساز
docker compose --profile tools run --rm --build migrate

# داده را برگردان (روی اسکیمای موجود، با پاک‌کردن داده‌ی خالی قبلی)
cat ~/arion-*.dump | docker compose exec -T db pg_restore -U routine -d routine --clean --if-exists --no-owner

# حالا خود اپ
bash deploy/update.sh
```

`deploy/update.sh` خودش build + migrate + up + انتظار برای healthy را انجام
می‌دهد؛ دستی این مراحل را جدا نزن (دلیلش در خود فایل توضیح داده شده).

## ۴) nginx و TLS

`deploy/nginx.conf.example` را با دامنه‌ی خودت در
`/etc/nginx/sites-available/routine-app` بگذار و لینکش کن. اگر Cloudflare
جلوی سایت است، همان نسخه‌ی HTTP کافی است؛ اگر نه، `certbot --nginx` را روی
سرور جدید اجرا کن (گواهی قدیمی به سرور جدید منتقل نمی‌شود).

## ۵) crontab

```bash
crontab -e   # خط‌های deploy/cron.example با CRON_SECRET و دامنه‌ی واقعی
```

⚠️ خط `economic-calendar` را **اضافه نکن**: در دیپلوی داکری، `cluster.js`
خودش این sync را از داخل کانتینر انجام می‌دهد؛ اگر هر دو باشند دوبار اجرا
می‌شود.

## ۶) تست قبل از سوییچ DNS

سرور جدید را با IP مستقیم (یا یک رکورد موقت مثل `new.دامنه`) تست کن:

- `curl -I http://<NEW_IP>/api/health` → ۲۰۰
- `curl -I http://<NEW_IP>/api/ready` → ۲۰۰ (این یکی واقعاً به دیتابیس می‌زند)
- ورود با یک حساب واقعی، دیدن برنامه‌ها/تریدها → یعنی restore درست بوده
- یک نوتیفیکیشن تستی → یعنی VAPID درست منتقل شده
- `docker compose ps` → همه `healthy`

## ۷) سوییچ DNS با کمترین قطعی

1. **۲۴ ساعت قبل** TTL رکورد A را روی ۳۰۰ ثانیه بگذار.
2. لحظه‌ی سوییچ: روی سرور قدیمی سایت را read-only/خاموش کن
   (`docker compose stop app`)، **یک dump تازه بگیر** و روی سرور جدید
   restore کن — وگرنه هر چیزی که کاربرها بین بکاپ اول و سوییچ ثبت کرده‌اند
   از بین می‌رود.
3. رکورد A را به IP جدید تغییر بده.
4. سرور قدیمی را **روشن نگه دار** (حداقل ۴۸ ساعت) تا کاربرهایی که هنوز DNS
   کششان قدیمی است سایت خالی نبینند؛ ولی اپش خاموش بماند تا دوجا نوشته نشود.

## ۸) بیرون از سرور: چیزهایی که به IP گره خورده‌اند

اگر دامنه عوض نشود، اکثر سرویس‌ها نیازی به تغییر ندارند. این‌ها را چک کن:

- **Google OAuth**: اگر دامنه همان است، redirect URI تغییری نمی‌خواهد.
- **ملی‌پیامک / درگاه پرداخت (Zibal) / گیت‌وی AI آروان**: اگر روی پنلشان
  IP allowlist فعال کرده‌ای، IP جدید را اضافه کن — این شایع‌ترین چیزی است
  که بعد از مهاجرت «بی‌صدا» می‌شکند.
- **Cloudflare**: اگر پروکسی روشن است، فقط رکورد A.
- **Search Console / اینماد**: دامنه ثابت است، کاری لازم نیست.

## ۹) بعد از سوییچ

- یک بکاپ خودکار روزانه روی سرور جدید بگذار (همان `pg_dump -Fc` در cron +
  کپی به یک فضای بیرونی). قبل از این، **سرور قدیمی را پاک نکن**.
- بعد از چند روز پایداری: آخرین dump سرور قدیمی را نگه دار و بعد سرور را
  حذف کن.

## اشتباه‌های رایج که سایت را بی‌صدا می‌شکنند

| اشتباه | نتیجه |
|---|---|
| `NEXTAUTH_SECRET` جدید | همه از حساب بیرون می‌افتند |
| VAPID جدید | push‌ها بی‌صدا نمی‌رسند (خطایی هم دیده نمی‌شود) |
| `TRUST_PROXY_HEADERS` فراموش شود | rate limit همه‌ی کاربرها را یک IP می‌بیند → قفل‌شدن ورود |
| بکاپ قبل از آخرین لحظه گرفته شود | داده‌ی بین بکاپ و سوییچ گم می‌شود |
| cron تقویم اقتصادی هم‌زمان با cluster.js | sync دوبرابر و فشار بی‌دلیل روی فید |
| `docker compose up -d` بدون `--build` | کد قدیمی بالا می‌آید، بدون هیچ خطایی |
